## 2026-09-24 — Milestone 8: room interactables — one generic `object:interact` event, proximity + E over raycast/click, the table's sit-down mode reuses existing camera/avatar machinery, a physical soundboard console reuses `sound:play` as-is

**Decided**, closing out Milestone 8. Scope was expanded live with the user beyond the roadmap's original one-line description ("additional 3D objects... a dice tray, shelf, etc.") — asked what M8's interactable(s) should actually be and how they should trigger, and the user specified three: the table switching between "wander the room" and "sit at the table" modes, a toggleable light, and (explicitly offered as optional, "maybe... cook something cool and funny up for this") a physical wall/floor soundboard console with large clickable buttons. All three landed.

1. **One generic `object:interact` event (`shared/src/interactables.ts`) covers every interactable, dispatched server-side by a string `objectId`** (`server/src/sessionStore.ts`'s `toggleLight`/`toggleSeated`, chosen in a `switch` in `server.ts`), rather than a dedicated event per object — this is the event name `docs/engineering/architecture.md` already suggested ("will need their own event(s), e.g. `object:interact`") written literally. Neither mutation is host-gated: `toggleLight` flips a session-wide flag (nothing to protect — it affects everyone equally, like a real light switch), and `toggleSeated` only ever flips the *requesting* player's own `seated` flag (the payload's `playerId` is always the actor, never a target), so there's no way to sit another player down. **Rules out:** a per-object event/type explosion for what's currently two behaviors, and host-gating either — reserved for if a future interactable actually needs it.
2. **Trigger model is proximity + a keypress (E), not raycast/click like table drawing** — an explicit user choice over the alternative (asked via `AskUserQuestion`). A pure `nearestInteractable(position, interactables)` function (`client/src/three/interaction.ts`, unit-tested) checks XZ distance each frame against a small fixed list of `{id, position, range}` entries; a `document`-level `keydown` listener for `KeyE` triggers whichever is nearest. Deliberately *not* gated by pointer-lock state (unlike drawing, which contends with the mouse for both look and draw) — a player can trigger an interactable whether they're mid-WASD-walk (pointer locked) or not, since E doesn't compete with anything. **Exception, logged as a deliberate deviation from the blanket "E" answer:** the soundboard console's individual buttons are raycast/click-triggered instead, gated the same way table drawing is (mouse free, not pointer-locked) — a single keypress can't disambiguate *which* of several buttons, so proximity+click (the established precedent from Milestone 5) fits better there than proximity+E does. Surfaced and accepted as a sensible carve-out, not silently done.
3. **The table's "sit down" mode is implemented as a pure camera takeover (`FirstPersonController.sit()`/`stand()`), not a new player state machine.** Sitting stores the current camera position/quaternion, releases pointer lock (so the *already-existing* raycast-driven interactions — drawing, dice clicks, the soundboard console — work immediately without any new code, since they're already gated on "not locked"), and repositions the camera to hover above the table looking straight down; `update()`'s existing `if (!isLocked) return` early-exit disables WASD for free, with no separate "is seated" movement guard needed. Standing restores the exact prior position/orientation and leaves the player to resume via the ordinary "click to look around" overlay (deliberately **not** auto-relocking pointer lock — some browsers only grant `requestPointerLock()` from a direct click gesture, and a silent relock would be inconsistent with every other unlocked state in this app). **Rules out:** teleporting the player's actual `position` to a seat slot (would need new collision/seat-assignment logic for no real benefit, since avatars are still placeholder capsules) — only the *visual* squash communicates "seated" to everyone else (see next point), never a position change.
4. **A seated player's `Player.seated: boolean` is genuine shared `GameState`, broadcast like any other ack'd mutation — but the local camera's sit/stand is applied optimistically on the keypress, not gated on the round-trip.** Two independent effects triggered by one E-press: `controller.sit()`/`stand()` fires immediately (a pure client-side view decision, no reason to wait on a network round-trip for a local camera cut), while `onObjectInteract('table')` separately updates server state so *other* players' view of this player updates too (`PlayerAvatars` squashes/lowers a seated player's capsule to ~55% height — the clearest "visible to everyone" signal available without real character animations). A rejoin/reload while `GameState` already has the player seated (the flag lingers across a disconnect, same as every other per-player status in this project) is reconciled once at room-load time by checking the fresh `GameState.players` snapshot and calling `controller.sit()` immediately if needed — without this, a reloaded client's local `isSeated` would start `false` while the server still says `true`, and the next E-press would desync the two by toggling the server *back* to standing instead of sitting the rejoined player down.
5. **`player:move` is skipped entirely while seated** (`RoomView.tsx`'s animate loop no-ops the whole send-if-moved block when `controller.isSeated`) — necessary, not just tidy: without this, the camera's teleport to/from the top-down hover position would itself register as a large `player:move` delta and broadcast the player's position as floating above the table to everyone else, which is wrong (the server-side `position` field is deliberately never touched by sit/stand, only the client-local camera is).
6. **The soundboard console (`client/src/three/SoundboardConsole.ts`) is presentation only — it adds zero new server logic**, reusing `sound:play`'s existing host-gate/ack/broadcast exactly as the 2D panel does. Its buttons are rebuilt from `GameState.soundboard` on every change (same `sync()`-from-full-snapshot pattern `DiceManager` uses), capped at 6 — the rest of a growing (built-in + uploaded) soundboard stays reachable through the existing 2D panel. Button size was deliberately generous (`BUTTON_RADIUS = 0.16`, doubled from an initial smaller pass) after live testing showed a small button is a genuinely difficult click target at typical in-room viewing distance — "large buttons" per the user's own framing turned out to be a real usability point, not just flavor text.
7. **A real, reproducible bug was caught and fixed during live two-tab verification, not by code review:** the E-press prompt text ("sit at the table" vs. "stand up") failed to update on the sit/stand transition, because the change-detection check that gates `setInteractionPrompt` compared only the *nearest interactable id* — which stays `'table'` in both the "standing near it" and "seated at it" states — never noticing that the `seated` flag (which `promptFor()` also depends on) had changed. Fixed by deduping on a combined `${nearestId}|${seated}` key (`lastPromptKeyRef`) instead of `nearestId` alone. Caught by directly driving the camera position via an injected debug hook and a real `KeyE` keypress (Chrome blocks synthetic pointer-lock clicks needed to drive WASD under automation, the same limitation logged since Milestone 3 — this is the first milestone where that gap was worked around well enough to catch a real bug live rather than resting entirely on unit tests).
8. **Sitting also switches the viewport to a square frame** (`RoomView.tsx`'s `applyViewportSize`, called from `FirstPersonController`'s camera + the mount effect's `renderer`/`container`), a follow-up user request ("the table should be full screen... it therefore needs to be square") once they saw the seated view in action. A round table naturally reads as "full screen" in a square frame, not a widescreen one — a widescreen aspect at a fixed vertical FOV either crops the table's top/bottom or leaves the table looking small with wasted space on the sides. `SEATED_HEIGHT_ABOVE_TABLE` (`FirstPersonController.ts`) was retuned from 2.1m to 1.65m to match — computed from the fixed 70° vertical FOV so the table's own radius fills the now-equal-on-both-axes frame with a small margin. The square canvas is centered via `.room-view`'s flexbox (harmless when it's full-size too, since standing's square-vs-full distinction collapses to "same size" there). **Rules out:** a dedicated orthographic top-down camera or a separate 2D-canvas overlay for the seated view — reusing the same perspective camera with a resized viewport is a two-function change, not a second rendering path.
9. **A small drawing toolbar (pen color/size, plus an eraser) appears only while seated** — the other half of the same follow-up request. `Drawing` gained `color`/`width` fields (`shared/src/types.ts`), chosen once when a stroke starts and carried on `DrawingStartRequest` (validated server-side with a `[1, 40]` width bound, `validation.ts`) — not resent per point, same "only the delta" principle the event already followed. `TableCanvas` now paints each stroke in its own stored style instead of one hardcoded color/width for the whole table. The eraser reuses the *existing*, previously-unwired `drawing:delete` event (implemented and unit-tested since Milestone 5, never actually triggered by any UI until now) via a new pure hit-test, `client/src/three/eraser.ts`'s `findStrokeNear` — point-to-segment distance to each stroke's polyline, minus half its own line width so a thick stroke is as easy to hit as it looks. **Rules out:** a per-point color/width (unnecessary — nothing in this app lets mid-stroke style changes happen) and a dedicated "delete a stroke" event (the exact semantics `drawing:delete` already had).
10. **Wiring up `drawing:delete` surfaced a genuine, previously-latent bug in its Milestone 5 implementation**, caught while implementing the eraser: `RoomView.tsx`'s `handleDrawingDelete` (the listener for *other* players' deletions) redrew from `activeSceneRef.current`, which still contained the just-deleted stroke — `drawing:delete` is a fire-and-forget delta event with no accompanying `session:state` broadcast, so a remote client's own copy of the scene never actually got the removal applied to it before the redraw ran, silently re-painting the stroke it was supposed to erase. The M5 exit-check test never caught this because it only asserted the broadcast *payload* arrived correctly, not that a receiving client's own derived visual state reflected it. Fixed by filtering the deleted drawing out of `activeSceneRef.current` locally before redrawing (mirroring the same local-optimistic-update pattern the eraser's own sender-side path needs for the identical reason) — a later unrelated `session:state` naturally overwrites this with the server's authoritative copy. Verified live with two tabs: erasing a stroke on one tab correctly removed it from the other's rendered table, not just from the eraser's own view.
11. **A same-session automation-testing gotcha worth recording**: verifying the color picker by setting `<input type="color">`'s `.value` directly and dispatching a plain `Event('input')` silently fails to trigger React's `onChange` — React's controlled-input tracking compares against its own internally tracked previous value and doesn't detect a value set outside its own setter, so the DOM swatch visually updates (native browser behavior) while the app's state never changes. The color stroke that "didn't work" during a first testing pass was this, not an app bug — confirmed by re-testing with the native value setter (`Object.getOwnPropertyDescriptor(HTMLInputElement.prototype, 'value').set`) before dispatching, and by inspecting the table's raw 2D canvas pixel data directly (bypassing the 3D scene's warm lighting/tone-mapping, which independently desaturates a chosen color quite a bit when rendered on the lit table surface — the same visual-only distortion already logged for the map-image upload). Two lessons for next time this pattern comes up: use the native setter for any React-controlled-input automation test, and when verifying a canvas-texture color end-to-end, check the underlying canvas's own pixel data rather than eyeballing the lit 3D render.
12. **The eraser's actual first user report ("worked once, then broken") turned out to be a real, more serious bug than point 10's** — not a click-precision issue as first suspected, and not something the earlier two-tab verification pass happened to catch, because that pass's incidental `sound:play`/reconciliation broadcasts (which fully refresh `activeSceneRef.current` from the server) papered over it by accident. The actual defect: `activeSceneRef.current.drawings` was never updated in real time as strokes were drawn — neither the local player's own `onStrokeStart`/`onStrokePoint` handlers nor the remote `handleDrawingStart`/`handleDrawingUpdate` listeners touched it, only the visible canvas texture did. Since `drawing:*` has no accompanying `session:state` broadcast (by design, per `docs/engineering/architecture.md`'s "Performance" section), a freshly-drawn stroke — by any player — was invisible to `findStrokeNear`'s hit-test until some *unrelated* event happened to trigger a full state refresh. In practice this meant erasing usually failed for anything drawn in the current sitting, working only for strokes that predated it (e.g. from before a reload) or when the player happened to also click a sound/light first. Fixed by updating `activeSceneRef.current.drawings` directly in all four handlers (append on start, append-point on update, mirroring the same pattern already used for the delete/erase paths) — verified by drawing a brand-new stroke and immediately erasing it, locally and (separately) across two tabs, with no incidental broadcast in between either time. **Rules out:** treating `drawing:*`'s delta-only design as "fire and forget locally too" — anything that needs to *read back* the current stroke list (not just paint it) has to maintain its own copy in step with every delta, the same requirement `drawing:delete`'s fix (point 10) already established for deletions specifically.

**Verified:** `server/src/interactables.test.ts` (4 tests) — a fresh session starts with the light on and nobody seated; one player's light toggle is seen live by another and can be toggled back off/on, not host-gated; a player sitting only ever changes their *own* seated status, seen live by everyone, and can stand back up; an unrecognized `objectId` and a malformed payload are both rejected without crashing. Break-round done on the `session:state` broadcast (disabled, confirmed both "seen live" assertions correctly fail/time out, restored). `client/src/three/interaction.test.ts` (5 tests) and `client/src/three/eraser.test.ts` (6 tests) cover the proximity and stroke-hit-test math in isolation. `client/src/three/PlayerAvatars.test.ts` extended (now 8 tests) — a seated player's avatar squashes, and `updateOne` (driven by `player:move`, which a seated player never sends) is confirmed to always apply as standing, documenting why the RoomView-level gating in point 5 above is load-bearing. `server/src/validation.test.ts`/`sessionStore.test.ts`/`tabletopMap.test.ts` extended for `Drawing`'s new `color`/`width` fields, including a width-out-of-bounds rejection case. Full `sanity-check` (lint/format/build/test, 208 tests across all 3 workspaces) clean. **Real two-tab browser verification, working around the Chrome pointer-lock restriction by directly driving the exposed camera object and dispatching real `KeyE`/click input via the automation tooling:** the light toggle dimmed the room and the lamp prop visibly, synced live on both tabs, including the mover's own avatar reflecting its new position; sitting switched the camera to a correct top-down, table-filling square view and hid the normal "click to look around" prompt; the seated player's avatar squashed on the other tab; standing restored the original view exactly; the soundboard console's buttons correctly raycast-hit and triggered `sound:play` for the host (rejected server-side for a non-host, same as the 2D panel); the drawing toolbar's color and eraser both verified correct via the table's raw canvas pixel data (not just the lit 3D render). **A follow-up user report ("eraser worked once, then broken") led to a second, more thorough verification round after the fix in point 12:** drew a brand-new stroke and erased it immediately with zero other actions in between (repeated for three separate strokes in a row, all first-attempt successes), then repeated the same check across two tabs — one player drawing, the other erasing that stroke immediately — confirming the fix holds for both the local and remote code paths, not just the case the first pass happened to exercise. No console errors in any of the above.

## 2026-09-24 — File uploads (M5/M7 extension): REST upload + socket-register two-step, soundboard becomes real shared state, cover-fit stopgap for map images

**Decided.** Not a numbered milestone — a user-requested extension of M5 (map background) and M7 (soundboard) landed between M7 and M8: players can upload a sound file to the shared soundboard, and the host can upload a map image instead of only pasting a URL.

1. **File uploads go over REST (`multer` + `express.static`), not Socket.IO binary frames**, and the flow is always two steps: `POST /uploads/images` or `/uploads/sounds` returns a URL, then the client sends that URL over the existing socket event (`scene:update` for maps, a new `sound:upload` for sounds) exactly as if the user had pasted a link. This means the server's socket handlers never special-case "uploaded" vs. "linked" — a URL is a URL — and the multipart-handling code stays entirely separate from the game-state/socket code. Files land in `server/uploads/{images,sounds}/` (gitignored, ephemeral — consistent with `SessionStore`'s own in-memory, restart-wipes-everything state) with randomized filenames (`randomUUID()` + original extension), size caps (10MB images / 8MB sounds) and an explicit mimetype allowlist enforced by `multer`'s `fileFilter`. **Rules out:** sending file bytes through Socket.IO, which would mean either buffering whole files in a socket handler or building a custom chunking protocol for something HTTP already does well.
2. **The soundboard became genuine shared session state (`GameState.soundboard: SoundState[]`), seeded from a new `BUILTIN_SOUND_PRESETS` constant, instead of M7's purely client-side static catalog.** `SoundState` gained a `url` field (`''` means "built-in synthesized preset," a set value means "play this uploaded file") so one array now represents both kinds of sound without a discriminated-union type or a second parallel list. The server never gains any audio-synthesis knowledge — it just stores `{id, name, url}` — while the client's `TONE_PARAMS` (the actual oscillator frequency/waveform/duration per built-in preset id) stays exactly where it was, now just consulted only when `url` is empty. `sound:play` gained a new server-side check (`SessionStore.hasSound`) rejecting an unrecognized `soundId`, since the id space is no longer a small fixed enum the server can implicitly trust. **Rules out:** a client-only soundboard catalog, which couldn't make an uploaded sound visible to other players at all.
3. **Uploading a sound is open to any player, not host-gated** — matching M6's dice precedent (any player can add to shared, visible-to-everyone state) rather than M7's `sound:play`, which stays host-only as before. Adding a sound to the board and triggering it for the whole room are different-enough authority questions that they don't need to share a gate.
4. **A cheap "cover fit" (`client/src/three/imageFit.ts`'s `computeCoverRect`, CSS `object-fit: cover`-style aspect-preserving crop) replaced straight stretch-to-fill for the table's background image**, landing as a partial, non-interactive response to the user's mid-session ask for "resize and fit [an uploaded map] to the circular table." The full interactive resize/reposition tool (crop/zoom/pan) they actually described is out of scope for this extension and stays tracked in `docs/roadmap.md`'s "Later" section. **Rules out:** leaving the old stretch-to-square behavior, which visibly distorted any non-square uploaded/linked image.
5. **The user's three other related asks that surfaced mid-session (standard/built-in map presets, wall drawing + a pen tool, a full-screen "sit down" tabletop mode) were captured as roadmap entries, not implemented now** — they read as a documentation-capture request ("if not [in the docs], add it to the roadmap"), not an immediate implementation mandate, and each is materially bigger scope than this upload extension. Logged verbatim reasoning in `docs/roadmap.md`'s "Later, out of scope for now" section.

**Verified:** `server/src/uploads.test.ts` (5 tests, real `fetch`/`FormData`/`Blob` against a listening server) — valid image upload+serve, rejected mimetype, oversized file rejected, valid audio upload+serve, rejected audio mimetype. `server/src/soundAndMute.test.ts` extended (now 9 tests) — a fresh session already has the built-in presets; a non-host player's uploaded sound is added to the shared soundboard, seen live by everyone, and can then be played by the host; `sound:play` rejects an unrecognized id; `sound:upload` rejects a duplicate id. `client/src/three/imageFit.test.ts` (4 tests) covers the cover-fit math in isolation. Full `sanity-check` (lint/format/build/test, 189 tests across all 3 workspaces) clean. **Real two-tab browser verification**: a non-host player's uploaded sound file appeared live in both tabs' soundboard lists with a Play button visible only on the host's tab; the host playing it and playing a built-in preset both produced no console errors; the host uploading a map image produced a visible, synced table-texture change on both tabs (confirmed via the POST and the subsequent image GET both returning 200, plus a matching visual shift on both tabs) with no console errors, including for a later joiner whose initial `session:state` already carried the uploaded background.

## 2026-09-24 — Milestone 7: soundboard & mute — synthesized tones instead of audio assets, self-mute plus host moderation, sender included in the sound broadcast

**Decided**, closing out Milestone 7.

1. **`sound:play` is host-only** (the roadmap's own stated default scope, taken as-is rather than re-litigated), while **`player:mute`/`player:unmute` are not purely host-gated: a player can always mute/unmute *themselves* (self-service, like muting your own mic), and the host can additionally mute/unmute *any* player (moderation)** — `SessionStore.setMuted` checks `actorId === targetPlayerId || isHost` rather than requiring host for every call. `docs/engineering/architecture.md`'s authority list names "Spieler muten" as needing server validation without saying who may trigger it; self-service mute is such an expected baseline capability (nobody should need to ask the host to mute their own mic) that leaving it out felt like an oversight in the spec, not a deliberate restriction. **Rules out:** requiring the host for every mute/unmute call, which would make a player unable to mute themselves.
2. **`muted` is a visible status flag only — this app has no voice chat to actually silence.** Worth stating plainly since the original spec's field name invites the assumption that muting does something functional; there's no microphone/audio-stream feature anywhere in this project to mute. The M7 exit check ("a muted player's state is visible to the group") is exactly this: a status indicator, not audio control.
3. **Soundboard sounds are synthesized tones (Web Audio `OscillatorNode`), not audio asset files.** No real sound effect files are available in this project, and generating one from a `{frequency, waveform, durationMs}` triple needs no asset pipeline at all — the same placeholder-quality tradeoff as colored capsule avatars instead of real character models, or a parchment canvas instead of real map art. A single shared, lazily-created `AudioContext` (not one per play) is reused across plays and `.resume()`d if suspended, handling the browser autoplay policy uniformly.
4. **`sound:play`'s server broadcast includes the sender** (`io.to(sessionId)`, not `socket.to(sessionId)` like `player:move`/`drawing:*`), and the client never plays a sound optimistically on trigger — every client, host included, only plays once the broadcast arrives. Unlike drawing/movement, there's no local-prediction reason to special-case the sender: a sound has no persisted GameState to update, so the broadcast *is* the only place playback is triggered from, and skipping the sender would mean the host who clicked the button never hears their own cue. **Rules out:** reusing `player:move`/`drawing:*`'s sender-excluded delta pattern here — it doesn't fit an event with no local optimistic effect to avoid double-applying.

**Verified:** `server/src/soundAndMute.test.ts` (5 tests) — a host-played sound is received by every client including the host itself; a non-host is rejected; a self-mute and a host-initiated mute of another player are each seen live by everyone; a non-host is rejected from muting someone else while the host succeeds; malformed payloads are dropped without crashing. Break-round done on both halves (the sound broadcast and the mute broadcast disabled separately, each confirmed to fail the matching assertion, then restored) — the mute break-round also surfaced a real test-timing bug unrelated to the server: a `.once()` listener registered right after two `session:join` calls could catch an already-in-flight "player joined" broadcast instead of the later mute broadcast, fixed by draining the pending broadcast with a short delay before registering the listener, the same pattern already used elsewhere in this suite for late-arriving state. Full `sanity-check` (lint/format/build/test, 180 tests across all 3 workspaces) clean. **Real two-tab browser verification**: the host's Soundboard/Map panels are correctly hidden from a non-host player (only a self-Mute button and the Dice panel show); a host-played sound produced no errors on either tab; a self-mute and a host-initiated unmute of another player each appeared live on both tabs with no refresh.

## 2026-09-24 — Milestone 6: dice — server-authoritative result, motion decoupled from the result label, `Dice.sceneId` dropped

**Decided**, closing out Milestone 6.

1. **The roll result is decided entirely server-side (`SessionStore.rollDice`'s `Math.random()`), never trusted from the client**, matching `docs/engineering/architecture.md`'s "Autorität und Synchronisierung" (dice are explicitly listed as needing server validation) and the client-side precedent already set for `player:move`/collision — the server is the one source of truth for anything a client could otherwise fake. `dice:spawn`/`dice:roll`/`dice:remove` reuse `scene:*`'s ack + full-`GameState`-broadcast pattern (infrequent — nobody rolls dice many times a second — unlike `player:move`/`drawing:*`'s fire-and-forget delta pattern), and none of the three are host-gated: the M6 exit check is explicit that *any* player can spawn/roll/remove a die.
2. **A die's visual "motion" (a spinning cube) is fully decoupled from its result label (a camera-facing sprite showing the number, or "?" before rolling).** Modeling a physically accurate cube that lands with the correct pip-face oriented upward would need real physics or at least carefully computed landing quaternions — disproportionate for a placeholder-quality die (consistent with capsule avatars instead of real characters, a parchment texture instead of real map assets, elsewhere in this project). Instead the cube spins for a fixed ~1s as pure visual flourish (satisfying "motion is visible"), while the label — independent of cube rotation — shows the current authoritative result ("visible" the other half of the exit check). **Rules out:** computing per-face landing orientations or integrating a physics engine for this milestone.
3. **`Dice`, unlike `Drawing`, has no `sceneId` — a deliberate difference, not an oversight.** A die is a physical object sitting on the table itself, not part of the 2D map layer; swapping the map underneath it (`scene:update`) shouldn't make it vanish or need special-casing, the same way a real die doesn't care what's printed on the paper under it. `GameState.dice` (already top-level in the original spec, unlike `Drawing`, which the spec *did* redundantly duplicate — see Milestone 5) turned out to already model this correctly; only `Dice.position: Vector3` needed adding (the original spec had no position field on `Dice` at all).
4. **Where a spawned die lands is picked client-side** (`client/src/diceSpawn.ts`'s `randomDiceSpawnPosition` — a random point within 60% of the table's radius, so it never spawns hanging off the edge) **and sent as part of the request, not computed by the server.** Mirrors `player:move`'s existing trust boundary: the server owns authority over results/outcomes (the roll), not over spatial reasoning about room geometry, which the server has zero knowledge of by design (collision is client-side only, per Milestone 3's architecture). Bounds validation for a client-supplied position is explicitly deferred to Milestone 9 ("host authority hardening"), same as it already is for player positions.

**Verified:** `server/src/dice.test.ts` (4 tests) — a spawn and roll are each seen live by another player; a die spawned by one player can be rolled/removed by a *different* player (confirming it's genuinely not owner- or host-gated); a later joiner's initial state includes an already-rolled die; malformed payloads are rejected without crashing the server. Break-round done on the exit-check test (the spawn broadcast disabled, confirmed the "seen live" assertion times out and fails, restored, confirmed it passes). `client/src/three/diceSync.test.ts` and `client/src/diceSpawn.test.ts` cover the pure add/remove/rolled diffing and spawn-position math in isolation, the same extraction pattern used for `tableCoordinates.ts`/`tableTopUV.ts` in Milestone 5 — `DiceManager` itself touches real `HTMLCanvasElement`/`THREE.Sprite` APIs unavailable under Vitest's `node` environment, so it's covered by the browser check below instead. Full `sanity-check` (lint/format/build/test, 154 tests across all 3 workspaces) clean. **Real two-tab browser verification**: spawning showed a die with a "?" label; rolling resolved and displayed a result (1, then re-rolled live to 4) visible on both tabs simultaneously, including the roll triggered by the *non-host* second player; removing made it disappear on the acting tab. No console errors on either tab.

## 2026-09-24 — Milestone 5: tabletop map & drawing — draw-on-the-physical-table interaction, canvas-texture pipeline, deliberate scope cuts

**Decided**, closing out Milestone 5. Two scope calls were made with the user up front (see the questions asked at the start of this work) before any code was written:

1. **Drawing happens by raycasting mouse input against the table's own mesh while pointer-lock is released — not a flat 2D overlay.** Matches `docs/engineering/architecture.md`'s framing of the map as "a physical surface on the table inside the room," not a floating UI panel. Concretely: releasing pointer lock (Esc, or never locking) shrinks the "click to look around" prompt from the full-screen button it was through Milestone 4 down to a small non-blocking pill at the bottom of the screen (`style.css`), freeing the rest of the viewport — including the rendered table — for direct click-drag interaction (`TableDrawing.ts`). A pointerdown/move/up sequence raycasts against the `Table_Top` mesh; a hit's local X/Z (relative to the table's own center) converts to canvas pixel coordinates (`tableCoordinates.ts`). **Rules out:** a separate 2D drawing-mode panel disconnected from the 3D scene.
2. **The table's canvas texture UV is recomputed in Three.js at runtime (`tableTopUV.ts`), not fixed in Blender.** Blender's default cylinder UV unwrap splits top/side/bottom into separate islands, not one clean 0..1 square — so a canvas texture applied via the mesh's real UV would display cropped/distorted. Recomputing UV from each vertex's local X/Z (mapping the inscribed circle onto the full unit square) sidesteps needing to fix this in Blender at all, and — critically — uses the exact same formula `tableLocalToCanvas` uses for raycast input, so a stroke always lands exactly where the player clicked. `TableCanvas`'s texture sets `flipY = false` so canvas-row-from-top maps directly to UV `v` with no inversion either function has to compensate for. **Verified this mapping is correct in a real browser**, not just via the two functions' matching unit tests: click-dragging on the table produced a stroke exactly under the cursor, and a test background image (a data-URI, to sidestep an external-network/CORS restriction in the sandboxed test browser — see below) filled the table's full circular top edge-to-edge with no crop or distortion.
3. **Scope cut, agreed with the user before implementation: one active scene per session that the host retargets by background-image URL (`scene:update`), not a multi-scene manager.** `scene:create`/`scene:change` are still implemented, validated, and unit-tested server-side (satisfying the roadmap's literal event list), but nothing in the UI calls them yet — only `scene:update`, against the one scene every session is seeded with at creation (`createDefaultScene`, mirroring M2's "implicit creation" pattern applied to scenes). **Rules out:** named multi-scene UI (creation form, switcher) for this milestone; a real follow-up if multi-map support becomes an actual need.
4. **`Drawing.points` changed from the original spec's `Vector3[]` to a new `Point2D` (`shared/src/types.ts`), and `GameState`'s top-level `drawings: Drawing[]` (redundant with `Scene.drawings`, and never consumed by any code before this milestone) was dropped.** A drawing stroke lives entirely on a flat canvas texture — reusing `Vector3` would leave `z` permanently unused, a footgun for a future reader who might assume it means something. Two sources of truth for drawings (top-level `GameState.drawings` *and* `Scene.drawings`, both in the original spec, keyed by the same `sceneId`) was clearly an oversight, not a deliberate design in the handed-over spec — grep confirmed nothing referenced `GameState.drawings` before this session touched it. Logged per `docs/engineering/architecture.md`'s own "Changing this spec" instruction (deviations get logged here and that file updated, not silently diverged).
5. **`player:move`'s pattern (no ack, no full-state broadcast, fire-and-forget, server rebroadcasts the same delta via `socket.to(sessionId)` excluding the sender) is reused as-is for `drawing:start/update/end/delete`.** Same justification as Milestone 4's entry: these can fire many times a second while a player drags a stroke. `scene:create/change/update`, by contrast, are infrequent and host-gated, so they keep `session:join`/`leave`'s pattern instead — a real ack plus a full `session:state` broadcast. Two different sync patterns living side by side in the same event model, chosen per-event by frequency/authority rather than picking one pattern for everything.

**Verified:** `server/src/tabletopMap.test.ts` (5 tests) — the host's `scene:update` is seen live by another player and rejected for a non-host; a drawing stroke is seen live point-by-point by another player and not just at the end; a later joiner's initial `session:state` already contains a fully-drawn stroke; `drawing:delete` is seen live. Break-round done on both halves of the exit check (scene broadcast and drawing broadcast disabled separately, each confirmed to fail the right test, then restored). `client/src/three/tableTopUV.test.ts` and `tableCoordinates.test.ts` cover the coordinate math in isolation (no DOM/canvas needed for that, unlike `TableCanvas`/`TableDrawing` themselves, which touch real `HTMLCanvasElement`/pointer-event APIs unavailable under Vitest's `node` environment and are instead covered by the browser check below — same split as `FirstPersonController`/`collision.ts` since Milestone 3). Full `sanity-check` (lint/format/build/test, 120 tests across all 3 workspaces) clean. **Real two-tab browser verification**, and it caught a real thing worth noting: an attempt to load a live Wikimedia Commons image as a background failed (`fetch(...).ok === false`) — an external-network/CORS restriction of the sandboxed test browser itself, confirmed by testing a `data:` URI generated in-page instead, which loaded and displayed correctly, edge-to-edge, with correct lighting. ## 2026-09-23 — Milestone 4: player avatars — yaw-only rotation, delta-only `player:move`, membership vs. live-movement split on the client

**Decided**, four related calls implementing Milestone 4.

1. **`Player` gained `rotationY` (yaw only, radians) — no pitch/roll.** A placeholder capsule avatar only needs to face a direction; tracking full camera orientation would be unused data pushed over the wire on every move. Computed from `camera.getWorldDirection()` (`FirstPersonController.getYaw()`), not read off `camera.rotation.y` directly — `PointerLockControls` manages pitch/yaw internally via a `'YXZ'`-order Euler that doesn't match `Object3D.rotation`'s own default `'XYZ'` decomposition, so reading `.rotation.y` directly would be quietly wrong once pitch is non-zero. **Rules out:** syncing full camera quaternion/orientation — more data than a placeholder capsule can even display.
2. **`player:move` is fire-and-forget, not acked, and rebroadcast as the same small delta (`socket.to(sessionId).emit`, excluding the sender) rather than folded into a `session:state` full-state broadcast.** Matches `docs/engineering/architecture.md`'s "Performance" section directly ("nicht bei jeder Änderung der komplette Game State übertragen") — this event fires up to ~10 times/second per moving player, so a full-`GameState` broadcast or an ack round-trip on every one would scale badly with player count. The server still validates and applies it (`SessionStore.move`, shape-checked in `validation.ts`) so a later joiner's initial `session:state` reflects everyone's current position — a malformed payload is silently dropped rather than acked with an error, since there's no ack channel to put an error on in the first place. **Rules out:** an ack-based request/response for movement, and reusing `session:state` for per-frame position updates.
3. **Client-side, avatar *membership* (who has a capsule at all) and *live movement* (where it currently is) are deliberately different code paths, not one.** `PlayerAvatars.sync(players, selfId)` runs only from `GameState.players` — infrequent, only on join/leave. `PlayerAvatars.updateOne(...)` runs from live `player:move` broadcasts — frequent. If a single path handled both, either movement updates would get needlessly reconciled against a stale `GameState.players` array on every frame, or a join/leave would require re-deriving live positions it doesn't have. Kept as two methods on the same class instead of two classes, since they share the mesh map. **Rules out:** re-running `sync()` on every animation frame.
4. **A new player's server-side default position/rotation is a real spawn point (`DEFAULT_SPAWN_POSITION`, shared between client and server), not the origin.** First tried `{x:0,y:0,z:0}` — harmless in Milestone 2 (nothing rendered a token there), but once avatars render from it, a freshly-joined player's own placeholder position defaults to underground-at-the-origin (`y - PLAYER_EYE_HEIGHT` math with `y=0` goes negative) until their first `player:move` corrects it. Moved the constant into `shared/src/types.ts` so `RoomLayout.ts`'s `PLAYER_EYE_HEIGHT` and `sessionStore.ts`'s `createPlayer` default derive from the same value rather than two literals that could drift. **Rules out:** leaving the mismatch as a "flashes briefly, self-corrects" cosmetic bug — cheap enough to fix at the root once noticed.

**Verified:** `server/src/playerMove.test.ts` — two real `socket.io-client`s, one moves, the other receives the broadcast live and the mover does *not* receive their own echo; a later joiner's `session:state` reflects an already-moved player's position; a malformed move doesn't crash the server. Break-round done on the exit-check test (removed the `socket.to(...).emit(...)` rebroadcast, confirmed the "sees it live" assertion times out and fails; restored, confirmed it passes). `client/src/three/PlayerAvatars.test.ts` (6 tests) covers create/update/remove/dispose in isolation — these construct real `THREE.Group`/`Mesh`/`Geometry` objects directly under Vitest's `node` environment; no WebGL/DOM needed for that. Full `sanity-check` (lint/format/build/test, 68 tests across all 3 workspaces) clean. **Real browser verification** (two Chrome tabs, via browser automation): both players join the same session, see each other in the roster, room renders without console errors. **Known gap, same as Milestone 3:** couldn't drive WASD movement itself through the automated browser to visually confirm a *moving* remote avatar end-to-end, because Chrome rejects the automation tool's synthetic clicks for Pointer Lock — confirmed directly this session (`document.pointerLockElement` stayed null after a synthetic click). Relied on the server integration test + client unit tests to cover what the browser check couldn't reach.

## 2026-09-23 — Milestone 3 part 1 implementation: axis-separated collision, `PointerLockControls`, room/table sizing

**Decided**, four related calls implementing the movement engine (see the split decision below for why this is "part 1").

1. **Collision is resolved one axis at a time (try X, then Z), not as a single 2D vector clamp.** `client/src/three/collision.ts`'s `resolveMovement` tries the candidate X move, rejects it outright if it would overlap the table (keeping the old X), then does the same for Z. This is what makes sliding along a wall or around the table happen for free — the blocked axis freezes while the open one still carries the player. Plus a final unconditional "safety net" pass (re-clamp to room bounds, push out of the table if still overlapping) that corrects an already-invalid starting position rather than assuming the caller always starts valid. **Rules out:** a naive single clamped-vector approach, which would either fully block a diagonal move that's only partially obstructed, or require a more complex sliding-vector projection for the same result this gets for free from doing axes separately.
2. **`PointerLockControls` (Three.js's own addon) drives movement, not a hand-rolled mouse-look/WASD implementation.** `FirstPersonController` calls `controls.moveForward`/`moveRight` (which do the camera-relative direction math, including flattening out pitch), captures the resulting position delta, and re-resolves *that* through `resolveMovement` before committing it — rather than reimplementing forward/right vector math to get a delta before moving. **Rules out:** a custom camera-direction implementation, which would just be reinventing what the addon already does correctly.
3. **Room 10m × 8m, round table radius 1.1m (≈2.2m diameter), player collision radius 0.35m, eye height 1.7m, walk speed 3 m/s.** Sized for the "round table, 4-5 players" direction the user chose, with room to walk behind seated positions. Pure placeholder numbers — expected to be superseded by whatever the real Blender export measures (`docs/engineering/blender-workflow.md`), not a spec to preserve.
4. **Joining a session now shows the 3D room as the main view, with the session panel (code, player list, leave) as a small fixed overlay in the corner**, rather than replacing it or hiding it behind a toggle. Keeps Milestone 2's functionality reachable without a second UI mode. Small/reversible — flagged here rather than asked, per the "small layout calls are fine to make and document" guidance; a real visual-identity decision (the room's actual look) was asked and answered separately, see below.

**Verified:** 13 unit tests on `resolveMovement` (walls, table, corner clamping, sliding, already-invalid start positions). Two-stage break-round: disabling only the table-overlap check left the three "walk straight into the table" tests passing (the unconditional safety net catches it too — intentional defense-in-depth, not a test gap, since the caller-facing contract is "never end up overlapping" regardless of which internal check catches it) but correctly failed the sliding test, which depends on the axis-separated logic specifically; fully gutting `resolveMovement` to a raw passthrough then failed 11 of 13 tests, confirming the suite as a whole is not vacuous. Restored and reverified passing. Full `sanity-check` pass (lint/format/build/test, all 3 workspaces, 43 tests total) clean, both before the merge and reverified after.

## 2026-09-23 — Milestone 2 design calls: implicit session creation, derived host role, disconnect ≠ leave, sessionStorage identity

**Decided**, four related calls made implementing Milestone 2 (`docs/roadmap.md`), none pinned down by the original spec:

1. **A session is created implicitly by its first joiner**, who becomes host. There's no `session:create` event — the spec's event list only has `session:join`/`session:leave`, and reading "join a code that doesn't exist yet" as "create it" avoids inventing an event the spec never named. **Rules out:** a separate creation flow/event for Milestone 2.
2. **Host/player role is derived, not stored per-player.** `GameState.hostId` already existed in the shared type; a player is host iff `player.id === state.hostId`. No new field on `Player`, no client-sent role claim possible — a client cannot fabricate host status because there's nothing to fabricate, only a comparison the server owns. **Host migration is explicitly out of scope**: if the host's player leaves, `hostId` keeps pointing at their now-absent id. Nothing crashes (no code dereferences `hostId` assuming a matching player exists), but there is currently no way for a session to get a new host once that happens. **Rules out:** building migration logic now — flagged for whichever milestone first needs host-gated actions to keep working after a host leaves (M5 `scene:*` is the first one that will need this).
3. **A raw socket disconnect does not remove the player from the session roster — only an explicit `session:leave` does.** This is what "a dropped client can rejoin the same session" (the M2 exit check) actually means: the `Player` record simply sits in `GameState.players` until either the same identity reconnects (`session:join` with the same `playerId` rebinds it to the new socket, no duplicate) or someone explicitly leaves. **Accepted downside:** a permanently-dropped client (closed tab, crashed browser) lingers in the roster forever, with no presence/timeout mechanism. **Rules out:** treating `disconnect` as an implicit leave, which would break reconnect entirely (the whole point of a dropped client rejoining is that their spot is still there).
4. **Client identity (`playerId`) is generated once and persisted in `sessionStorage`, not `localStorage`.** `localStorage` is shared across every tab of the same origin — two tabs of the same browser would collide onto one `playerId`, silently merging what should be two distinct players and breaking the "two browser tabs... see each other" exit check outright. `sessionStorage` is per-tab but still survives a same-tab reload, which is exactly the reconnect case this needs to support. **Rules out:** `localStorage` for this purpose, despite it being the more common default for "remember this across visits" — the per-tab requirement here overrides that.

**Verified:** `server/src/session.test.ts` connects two real `socket.io-client` instances against a real server and asserts each sees the other in the resulting player list, plus a disconnect/rejoin-same-identity/leave sequence. Break-round done on the core "Alice sees Bob join live" assertion (removed the room broadcast, confirmed the test times out and fails; restored, confirmed it passes). Also smoke-tested against the real `npm run dev` process pair (not just the in-process test) with two independent `socket.io-client` connections — functionally correct (both joins succeed, correct player lists in both acks), though the *broadcast* one of those manual clients happened to catch was the stale single-player self-broadcast rather than the later two-player one, because a one-shot `.once()` listener over a real network isn't guaranteed to catch a specific broadcast the way `waitForSessionState()` reliably does inside the same-process vitest test. Not a server defect: the real client (`App.tsx`) uses a persistent `.on()` listener, so it applies every broadcast in order and converges on the correct state regardless of which one a `.once()` happens to catch.

The spec itself notes the concrete libraries may be adjusted during implementation as long as the functional requirements hold — so this isn't a hard lock, just a default not worth re-deciding before any code exists. **Rules out:** spending Milestone 1 time comparing frameworks (e.g. Vue vs. React) without a concrete reason one is failing.
